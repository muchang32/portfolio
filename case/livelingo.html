精選案例

LiveLingo　把一場演講的即時字幕，做成能重複使用的工具

公司邀請國際講者來台演講，現場需要即時中文字幕。評估過幾套商用方案後，我自己做了一個 Chrome 擴充功能，在兩場活動實際使用。

角色
自行開發與導入（聯經數位，資訊管理師）
類型
Chrome 擴充功能 ・ 活動現場即時字幕
團隊
個人開發；資服部 AI 小組（約 6 人）內部測試
負責
需求定義 ・ 開發 ・ 現場測試與調整 ・ 命名與識別設計

問題

公司 2026 年 9 月邀請新聞設計顧問 Mario García 博士來台，內部工作坊與台北漢來大飯店的對外公開演講都需要即時中文字幕。

負責單位先盤點了市面上的方案，交給我們部門評估。我所在的 AI 小組每週會分享各自用過的工具與自己做的東西，經理在那次分享裡除了幾套商用服務，也放了一支 YouTube 影片 - 有人自己做了一個即時翻譯的瀏覽器擴充功能。

我實測了 Wordly 與 PowerPoint 內建的 CC 字幕；另外兩套 Felo Subtitles 與 Flitto 沒有免費試用，等於要在無法實測的情況下決定要不要付費，就沒有列入。

Wordly 的品質最好，但顯示樣式的調整彈性低、操作不直覺、收費偏高；PowerPoint CC 設定單純，但只收得到簡報者麥克風的聲音，接不到現場音訊或影片播放的聲音，字幕的行數、位置與樣式也全部固定。

判斷與取捨

自己做：預算可控，客製化沒有上限

技術上這件事門檻不高 - 擷取音訊、送語音辨識、送翻譯、把結果顯示出來。那支 YouTube 影片證明了可行。

我參考它的做法做出一個 Chrome 擴充功能，串接 Deepgram 語音辨識 API 與 DeepL 翻譯 API，再往下針對演講現場客製化。這個選擇換到兩件商用方案給不了的東西。

第一是預算可控。 商用方案的成本是報價單上的數字，用不用得順都一樣要付；自製的成本是兩支 API 的用量，而免費額度足以支撐幾場演講。要加功能不必重新議價，要停也不必解約。

第二是客製化沒有上限。 自己做最大的價值就在這裡 - UI 與使用流程都能自己調整：如何斷句、字體大小、字型粗細、字幕位置，以及要不要同時顯示原文，全部可以設定。

代價也很清楚：要自己申請並管理 API Key、用量超過免費額度就要付費，而且當時還沒發布，得用 Chrome 的開發者模式載入。在只辦幾場活動的前提下，這些都可以接受。

還有一個從一開始就定下來的限制：使用者不是我。

活動當天在現場操作的是部門負責設備的同仁，我人不在。這代表所有的調整都必須在介面上做得到 - 我沒辦法站在旁邊改程式。

這個限制後來決定了整套工具的做法。

示範影片為黃仁勳主題演講公開直播的實測畫面，非上述活動現場。

把意見做成選項，而不是照單全收

正式活動前，負責設備的同仁與經理在公司大會議室實際投影測試，並展示給幾位長官看。意見立刻就來了：字幕太小、位置太低、一句斷太長。經理在現場即時把意見傳給我，我收到就改、改完他們再看一次。

最快的做法是直接改到他們滿意。但我沒有這樣做。

因為下一場換了場地、換了螢幕、換了講者，同一組數字就不對了。照著改，等於每一場都要再找我改一次程式 - 而我不會在現場。

所以每一個意見我都往上抽一層，變成可以當場調整的選項：

收到的意見做成什麼
字幕太小字體大小可調
看不清楚字重可調
位置太低字幕高度可調
一句太長斷句長度可調

再加上為演講螢幕做的全螢幕模式、可隱藏的設定列，以及鍵盤快捷鍵 - 現場不可能讓人拿著滑鼠在螢幕上點來點去。

這一層抽象讓它從「為這場演講寫的程式」變成「可以用在下一場的工具」。

接受即時與準確不可兼得，但不停在那裡

活動後最尖銳的回饋來自幾位英文程度到口譯等級的長官：翻譯不夠精準。

這件事我認為他們是對的，但原因是結構性的。口譯員可以等講者講完一個完整的意思再翻，即時翻譯必須邊聽邊出字 - 速度與準確在當下是互斥的，這不是換一支 API 能解決的。

不過「做不到完美」不等於「只能這樣」。我回頭去查翻譯 API 有沒有可以介入的地方，找到兩個：

  • 帶上前文：把前幾句一起送出去，讓翻譯有上下文可以參考，代名詞和承接句會準很多
  • 自訂詞彙表：新聞設計領域有專有名詞，事先設定好，講者一講到就照設定翻

兩項都已經做進去了，會用在下一場。

成本：把「要不要付錢」變成「要不要花時間」

Deepgram 與 DeepL 都有相當大的免費額度，辦幾場演講都還在範圍內。這代表這套工具的邊際成本接近零 - 不必為了一場活動談授權、編預算、跑採購流程。

但它不是真的免費，只是把成本從「錢」換成「我的時間」，而且往後每一次要改都還是我。這筆帳在只辦幾場的情況下划算，如果變成常態服務就要重算。

命名與識別

我替它取名 LiveLingo，畫了一隻霓虹蜂鳥當 logo。蜂鳥快、而且能在空中定住不動，那正好是即時字幕要的兩件事：跟得上，而且穩。

一個內部工具要不要做 logo？我認為要。有名字、有識別，它才會被當成一個產品被討論、被記得、被下一次想起來用。

結果

兩場活動實際使用 - 內部工作坊與台北漢來大飯店的對外公開演講，現場的即時中文字幕都由這套工具產出。

現場負責導播系統的廠商主動給了回饋：他們辦過各種大型活動、看過許多即時翻譯工具，這套的翻譯速度與準確度在他們看過的裡面算好的。

公司為此特別頒發獎金。目前也在規劃把它上架到 Chrome 擴充功能商店。

反思

使用者的意見通常是答案，不是需求。

「字幕太小」是一個答案。它背後的需求是「我在這個距離、這個螢幕上看不清楚」。如果我照著答案改，解決的只有那一場；抽成選項，解決的是這一類。

這件事在做 Aicast 和自動配圖的時候也遇過 - 使用者說的是症狀，要往上找一層才會碰到真正要解的東西。只是那兩次我是在做別人開發的產品，意見要先變成需求單、排進開發、等到下一版才看得到結果；這次是經理在會議室把話傳回來，我改完他們當場再看一次，一來一回只有幾分鐘。中間沒有流程擋著，症狀和病灶的距離才這麼清楚。
